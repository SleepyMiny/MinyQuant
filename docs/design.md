# MinyQuant 금융 실행 설계

MinyAI에서 인계한 금융 계약의 정본이다. 아래 메인/서버는 실행 장비 역할이며 저장소 소유권을 뜻하지 않는다. MinyAI와의 연결은 [연결 계약](integration/minyai.md), 구현 순서는 [보드](implementation/BOARD.md)를 따른다.

### 6.1 책임과 데이터

메인은 분석·백테스트·전략/주문 후보를 만들고 서버는 데이터 수집, 결정적 위험 검사, 주문 실행, 체결/자금 원장, 대사, 비상 중지를 담당한다. LLM은 브로커 키·위험 한도 쓰기 권한을 갖지 않는다. 신호에는 생성 시각·사용 데이터·전략/모델 버전·유효시간·근거가 포함된다. 초기 전략은 저빈도 또는 서버에서 지속 실행 가능한 검증된 규칙으로 제한한다.

시장 범위는 국내·해외 모두다. 해외 국가·상품·첫 실전 시장·증권사는 아직 미정이다. 공통 모델은 다음을 포함한다.

- 종목 식별자, 거래소/거래 venue, 통화, 브로커 매핑. ticker 문자열만으로 식별하지 않는다.
- UTC 원시각, 거래소 IANA 시간대, 현지 거래일, 휴장/DST/조기폐장/세션. KRX/NXT 등 지원은 브로커별 기능표에서 검증한다.
- 가격/수량/수수료/세금은 Decimal과 명시적 통화/단위, 호가 단위·lot·최소금액·TIF·정정/취소 지원표.
- 통화별 결제완료·미결제·미체결 예약 현금, 보유/예약 수량, 환전·입출금·기업행사, 연결 담보와 계좌 전체 노출.
- 기준 통화 평가에는 환율 출처·시점이 필요하다. 일간 손익은 실현/미실현·환율 효과·일 경계·입출금 조정을 정의한다.

자동환전·통합증거금·미수/자동대출은 별도 권한 대상이다. 주문가능금액을 보유 통화 현금으로 간주하지 않는다. 초기 레버리지·신용·공매도·파생은 범위에서 제외한다. 과거에 언급된 실험금은 현재 한도나 거래 승인으로 사용하지 않는다.

시장 데이터는 원천/수집/공개 시각, 수정 버전, 원시/조정 가격, 기업행사를 보존한다. 미래 정보를 과거 전략에 섞지 않고 생존편향·시점 누수를 검증한다. 백테스트는 읽기 스냅샷으로 메인에서 수행하고 수수료/환율/슬리피지/세금 가정을 명시한다. 데이터 이용 조건·API 호출 제한·실시간/지연 여부는 실제 공급자 확정 후 확인한다.

상시 처리 순서는 **출처·게시/수집 시각·정정 관계 기록 → 중복 제거·정제 → 분류·요약 → 버전/해시를 고정한 분석 데이터셋**이다. 원본/정제/요약 사이의 참조와 처리 버전을 남겨 요약에서 근거·당시 이용 가능 시점까지 추적한다. 정정은 이전 스냅샷을 덮어쓰지 않는다. 원문 이용·보관·삭제 조건을 적용하며 보관 불가/만료 시 허용된 메타데이터와 근거 소실 상태를 남긴다. 24시간 수집은 경량 수집기·규칙·배치로 수행하고 대형 AI 상시 가동을 뜻하지 않는다. 수집·재분석 판단과 GPU 실행의 책임·ID·입출력·실패 계약은 [공개 연결 계약 v0.1](integration/minyai.md)에 둔다.

외부 뉴스·문서·요약·모델 출력은 비신뢰 데이터다. Quant 자체 수집기에서 URL의 스킴·실제 접속 IP·DNS 변경·각 리다이렉트와 크기/시간을 검사해 내부망·loopback·link-local·metadata 접근을 차단한다. 모델 출력의 스키마·값 범위·유한 수·종목 식별·근거·버전·만료를 검증하고 잘못된 값은 거부한다. AI의 종목 제안은 실행 권한이 아니며 승인·위험 게이트를 통과하지 않고 주문으로 전환할 수 없다. Quant 독립 시험 Q-A04~Q-A06을 코어 보안시험으로 대체하지 않는다.

### 6.2 자금 예약·전송·불확정 상태

1. 금융 실행부가 현재 데이터·시간·계좌 상태·승인·전략·손실/주문/총노출 한도를 검사한다. 필수 한도 미설정이면 실거래 불가다.
2. **금융 DB 하나의 트랜잭션**에서 승인 검증/소비 또는 위임 한도 차감, 현금/노출 예약, 주문 의도·outbox를 저장한다. 전략/시장 간 공유 담보도 잠금/직렬화 규칙으로 보호한다.
3. 계좌별 단일 실행 경로가 전송 직전에 실행권/fence, 승인 유효성, 안전 중지 latch, 조정 heartbeat, 시세/환율/계좌 상태의 신선도, 주문 만료를 재검사한다. 예약 뒤 outbox 대기 중 조건이 바뀌면 전송을 막는다. 이미 소비된 일회 승인은 동일 intent에 귀속된 소비 기록을 검증하며 다시 소비하지 않는다. lease가 만료된 옛 worker는 브로커 키를 직접 사용할 수 없어야 한다.
4. 브로커의 주문 ID/클라이언트 ID와 요청 ID를 연결한다. 송신/접수 여부가 불명인 timeout은 **UNKNOWN**이다. 새로운 ID를 만들어 재주문하거나 실패로 간주하여 예약을 풀지 않는다.
5. 주문·정정/취소·부분체결·잔고·현금·수동 HTS 거래·입출금·환전·기업행사까지 조회하고 대사한다. 페이지 끝까지 조회하고 체결 중복/역순/재연결을 처리한다. WebSocket 이벤트만으로 정본을 확정하지 않는다.
6. UNKNOWN 진입 즉시 영향 계좌의 안전 중지 latch를 영속화하고 신규 위험 확대를 차단하며 조회·대사를 수행한다. 해소 후에도 사고 재승인 정책을 따른다. 예약 해제는 확인된 최종 상태 또는 검증된 대사 결과로만 한다.

외부 브로커 전송은 DB 트랜잭션에 포함되지 않는다. 대사로 중복/불확실성을 관리하며 손실 한도는 갭·슬리피지·시장 중단에서 손실 금액을 보장하는 장치가 아니다.

금융 DB와 일반 DB를 한 PostgreSQL 인스턴스에서 시작할 수는 있지만 별도 계정/권한을 둔다. 이는 호스트 관리자 침해·디스크 고장·자원 고갈의 격리가 아니다. 금융 승인 사용·예약·의도를 일반 DB에 분산하지 않는다. PostgreSQL의 일반 연결은 하나의 DB에 접근한다는 점을 반영한다. [공식 DB/스키마 설명](https://www.postgresql.org/docs/current/ddl-schemas.html)

### 6.3 중지와 재개

| 상황 | 재개 정책 |
|---|---|
| 승인된 운영 실행부가 기록한 정상 계획 재시작 | 유효한 사전 위임, 동일 정책/전략, 전체 대사, 건강한 저장소/시각/신선한 데이터, 안전 중지 없음이 모두 충족되면 자동 재개 가능 |
| UNKNOWN, 계좌 불일치, 손실 한도, kill switch, 키 침해, 원인불명 종료 | 안전 중지 사유를 영속 저장. 원인 해소·대사 후 사용자 재승인이 있어야 재개 |

안전 중지 latch는 재부팅·새 거래일·대사 성공으로 자동 해제하지 않는다. 에이전트가 사고를 계획 재시작으로 다시 분류하지 못하게 한다. kill은 신규 주문 차단과 사전 정책에 따른 미체결 취소다. 강제 청산은 별도 승인·정책이며 계좌 불명 상태의 매도를 무조건 위험 축소로 취급하지 않는다. 통신 단절 때 취소/청산 성공을 가정하지 않고 독립 브로커 접근 경로를 유지한다.

진입 순서는 fake broker/replay → 읽기 전용 연결 → 시장별 모의 → 구체적 한도와 위임을 가진 제한 실전이다. 일정 일수의 모의나 높은 백테스트 수익만으로 승격하지 않는다. 기능·장애·대사·운영 시험과 사용자의 현재 위임이 필요하다.

### 6.4 전략 평가·총비용·운영 제한

목표는 전체 비용을 포함한 지속 가능한 운용이며 수익·무손실을 보장하지 않는다. 시스템 안전성 통과와 전략 성과·경제성 판정은 별도다. 비용 반영, 개발/튜닝에 쓰지 않은 기간, 동일 평가 기간·자본의 단순 기준전략 비교를 요구한다. AI/GPU 추가 방식은 경량 규칙·낮은 분석 빈도 대비 증분 비용과 개선을 함께 평가한다. 장중이라는 이유만으로 GPU를 계속 켜거나 데이터/버전/필요성이 변하지 않았는데 같은 유료 분석을 반복하지 않는다. 분석 빈도·모델·장비는 품질·응답시간·비용으로 선택한다.

- 거래 비용: 적용 수수료·세금·스프레드·슬리피지·환전 비용을 비용 모델 버전과 함께 기록한다. 백테스트 예상 비용과 실제 체결·정산 비용을 구분하고 `included_in_pnl` 등으로 체결 가격/손익에 이미 포함된 비용의 재차감을 막는다. 실제 비용 전 손익을 복원할 수 없으면 추정/미확인으로 표시한다.
- 운영 비용: 서버/메인 전기료, 모델/API, 시장 데이터, 클라우드·저장을 기록한다. GPU 실행뿐 아니라 부팅·모델 로딩·대기 시간도 측정한다. 기존 장비 공통 유지비와 Quant 증분 비용을 나누고 공통비 배분 기준을 공개한다. 신규 구매·감가상각은 별도 경제성 항목으로 두어 현금 지출/배분 비용과 이중 합산하지 않는다. 무료 크레딧 적용 실제 청구와 종료 후 정상 요금 시나리오를 구분한다.
- 보고: 거래 손익, 거래 비용 차감 후 손익, 시스템 운영비까지 차감한 프로젝트 순손익을 같은 기간·기준 통화로 구분한다. 입출금은 수익에서 제외한다. 각 비용에 금액/통화·기간·실제/추정/미확인·기준일·출처·귀속/포함 여부를 둔다. 미확인을 0원이나 유리한 확정값으로 바꾸지 않으며 순손익도 미확정 또는 근거 있는 범위로 표시한다.
- 게이트: 연구·모의는 사용자 승인 실험 예산 안에서 진행한다. 실거래 진입·규모 확대는 비용 반영 성과·최대 낙폭·손익분기 조건·비용 증가 시나리오를 별도 검토한다. 백테스트/AI 예상 수익은 자동 승인이 아니며 근거 부족은 **경제성 미검증**으로 남긴다.
- 집행: 사용자가 일간·월간 운영비와 실험 손실 예산을 확정한다. 유료 호출 등 통제 가능한 지출은 실행 전에 예약/확인하고 불명 비용·상한 초과 시 해당 유료 작업과 필요한 신규 위험 확대를 제한한다. 기존 주문 확인·대사·안전 중지·필수 기록은 계속한다. 단기 적자만으로 자동 청산하거나 전략을 변경하지 않는다.
